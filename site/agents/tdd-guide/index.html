01 — What it is

Guaranteed test-first discipline and regression prevention

The tdd-guide prevents the number one AI coding failure mode: writing code and declaring victory without proving it works. It demands a failing test first, watches it fail for the expected reason, implements the minimal passing logic, and refactors under a safe green harness.

Glossary for non-coders: Red-Green-Refactor: The core TDD cycle: write a failing test (Red), make it pass (Green), then clean up the code (Refactor). · Edge Case: Rare or extreme inputs (like an empty text box or zero bytes) that frequently crash untested code. · Code Coverage: The percentage of source lines and branches executed during test runs.

03 — Quality Checklist

Mandatory test scopes and non-negotiable edge cases

Sourced directly from agents/tdd-guide.md, every code addition must account for both happy and failure pathways.

Test Types Required
  • → Unit Tests: Individual functions tested in complete isolation with deterministic mocks.
  • → Integration Tests: Testing API endpoints, data persistence, and inter-module contracts.
  • → E2E Tests: Real browser testing with Playwright covering critical operator and user paths.
Mandatory Edge Cases
  • ! Null / Undefined & Empty: Null inputs, empty strings, and empty collections.
  • ! Boundary & Race Conditions: Min/max limits, concurrent async triggers, and timeout handling.
  • ! Error Paths & Special Chars: Network dropouts, DB errors, Unicode, emojis, and SQL chars.
04 — Procedure

The Red-Green-Refactor execution loop

  1. Step 1 — RED
    Write Test First

    Writes a test expressing the desired behavior before implementation exists.

    Failing expectation
  2. Step 2 — VERIFY RED
    Confirm Failure

    Runs test to verify it fails specifically for the expected reason.

    No false positives
  3. Step 3 — GREEN
    Minimal Code

    Writes only enough production code to turn the test green.

    Shortest passing diff
  4. Step 4 — REFACTOR
    Clean & Optimize

    Eliminates duplication, cleans naming; tests remain continuously green.

    Clean architecture
  5. Step 5 — GATE
    Coverage Audit

    Verifies 80%+ branch and statement coverage before commit.

    Coverage gate check
05 — Strict boundaries

What tdd-guide does NOT do

No "tests later" excuses

Never permits writing production code first with the promise of adding tests after the fact.

No implementation detail testing

Tests observable behaviors and output contracts rather than fragile internal component state.

No mock bloat

Avoids mocking what can be cleanly executed in memory; mocks external boundaries only (DB, network).
