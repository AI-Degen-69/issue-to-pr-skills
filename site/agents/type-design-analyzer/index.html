01 — What it is

Making illegal states unrepresentable

Unlike linters that look for syntax or runtime errors, the type-design-analyzer is a domain architecture critic. It inspects whether your structs, interfaces, and discriminated unions enforce business invariants at compile time rather than relying on defensive runtime if/else checks.

Read
Type Definition Context

Inspects type definitions, constructor signatures, getters/setters, and domain operations across modules.

Grep
Usage & Escape Hatches

Finds where callers bypass encapsulation or access internal properties directly from outside the module.

Glob
Schema & Domain Boundaries

Locates API contracts, schema migrations, and entity definitions across the entire workspace.

Glossary for non-coders: Invariant: a business truth that must always hold (e.g. "a shipped order must have a non-empty tracking code"). · Illegal State: a combination of fields that makes no real-world sense (e.g. status is "failed" but error is null). · Language-Agnostic: these principles apply equally to TypeScript, Rust, Go, Python, Kotlin, and Swift.
02 — The 4-dimension scoring rubric

Structured scoring grid over every inspected type

Sourced directly from agents/type-design-analyzer.md:21-41. Rather than emitting binary pass/fail gates, the analyzer scores each type across four architectural dimensions.

Dimension 1 Scope
Encapsulation

Are internal details hidden? Can invariants be accidentally violated from outside code?

Audit: public fields vs private methods
Dimension 2 Domain
Invariant Expression

Do the types encode business rules? Are impossible combinations prohibited at compile time?

Audit: tagged unions vs bag-of-optionals
Dimension 3 Utility
Invariant Usefulness

Do these type invariants prevent real bugs in production, or are they burdensome over-engineering?

Audit: real error prevention vs ceremony
Dimension 4 Compiler
Enforcement

Are invariants guaranteed by the compiler, or are there convenient escape hatches like any?

Audit: compile-time guarantee vs bypasses

03 — Code transformation example

From "bag-of-optionals" to impossible-states-prevented

Shown here with TypeScript syntax, but the architectural pattern applies identically in Rust, Go, Python, and Java.

WEAK: Bag-of-Optionals (Allows 16 illegal combinations)

Allows nonsensical states where status is 'success' but data is missing and error is set. 

interface AsyncResult<T> {
  status: 'idle' | 'loading' | 'success' | 'error';
  data?: T;
  error?: Error;
  isLoading?: boolean;
}

// Problem: allows invalid state:
// { status: 'loading', data: user, error: new Error('fail') }
Enforcement: Weak (0/5) — Code must check every field with runtime if statements everywhere.
STRONG: Discriminated Union (Zero illegal states)

Every state is mathematically distinct. Data is only accessible when status is 'success'. 

type AsyncResult<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error };

// Guaranteed by compiler:
// Cannot read .data unless status === 'success'
Enforcement: Strong (5/5) — Compile-time exhaustiveness check prevents unhandled failure modes.
Language universality note: In Rust this is an enum Result<T, E>; in Go it is a closed interface with unexported methods; in Python it is a Union of dataclasses with literal tags.
04 — When it runs

Concrete real-world trigger cases

1. Adding a new API field

When a PR adds an optional boolean or string to an API response, the analyzer checks if it conflicts with existing fields or should be grouped into an exclusive state.

2. Refactoring entity models

Audits user account or subscription types to ensure transitions (e.g. Free → Trialing → Active → Cancelled) cannot end up in split-brain states.

3. Complex configuration payloads

Checks that plugin configurations or webhook settings don't allow conflicting authentication strategies simultaneously.

05 — Output format

Per-type evaluation card

Directly matches agents/type-design-analyzer.md:43-50. Evaluates each type by name, 4 scores, overall assessment, and improvements.

TYPE: OrderShipmentStatus (src/domain/orders.ts:24)
Encapsulation
Moderate (3/5)
Invariant Expression
Weak (2/5)
Invariant Usefulness
High (4/5)
Enforcement

Overall Assessment: The type models shipment state with separate nullable fields (`carrier`, `trackingUrl`, `deliveredAt`) alongside a status string enum. Callers can represent an order as `status: 'delivered'` while `deliveredAt` is `undefined`.
Specific Improvement Suggestions: Split into a discriminated union by status. Require `trackingUrl` on `'in_transit'` and require `deliveredAt: Date` on `'delivered'`.
06 — Strict boundaries

What type-design-analyzer does NOT do

No binary merge gates

The analyzer outputs a qualitative scoring rubric and actionable architecture advice, not a strict Pass/Block gate.

No code execution (No Bash)

Uses only Read, Grep, Glob. It never runs compiler commands, shell scripts, or external binaries.

Does not rewrite types

Provides concrete improved type signatures in its review card, but leaves the refactoring in the engineer's hands.
