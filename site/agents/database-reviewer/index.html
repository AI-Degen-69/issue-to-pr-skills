01 — What it is

Guardian of data integrity, indexing, and transactional scale

The database-reviewer incorporates battle-tested Postgres patterns (including Supabase best practices) to ensure queries execute in milliseconds and migrations do not cause table locks or service downtime.

Read
Schema Context

Reads migration files, ORM schema definitions (Prisma/Drizzle), and existing table constraints.

Grep
Query Pattern Hunter

Searches for unindexed foreign keys, raw SQL interpolations, and loops generating N+1 queries.

Glob
Migration Discovery

Discovers migration sequences, SQL seed scripts, and database configuration manifests.

Bash
Diagnostic Command

Executes non-destructive SQL diagnostics like EXPLAIN ANALYZE or migration linting tools.

Glossary for non-coders: N+1 Query Problem: fetching a list of 100 items, and then issuing 100 separate database queries in a loop to get each item's details. · Sequential Scan: Postgres reading every single row on disk because an index is missing, grinding performance to a halt. · RLS (Row Level Security): fine-grained database rules ensuring User A can never read User B's rows.

03 — Review checklist

The 4-tier Database quality checklist

Sourced directly from agents/database-reviewer.md, focused on eliminating data corruption, slow queries, and locking traps.

CRITICAL — Performance & Security Traps

Flaws that cause immediate production database lockouts or data breaches.

  • ✕ Unindexed foreign keys: Foreign keys without indexes cause full table scans on parent table updates/deletes.
  • ✕ Missing RLS on tenant tables: Multi-tenant tables created without Row Level Security enabled.
  • ✕ Exclusive table locking migrations: Adding columns with non-null defaults without CONCURRENTLY or statement timeouts.
  • ✕ Overly permissive grants: Granting ALL privileges to the application database user role.
HIGH — Query Architecture & Schema Hygiene

Sub-optimal schemas that silently degrade throughput as data volume expands.

  • ✕ N+1 queries: Querying related records in application loops instead of SQL joins or eager includes.
  • ✕ Wrong composite index order: Ordering index columns by range before equality (must be equality first).
  • ✕ Missing ON DELETE clauses: Creating foreign keys without explicit CASCADE, RESTRICT, or SET NULL rules.
  • ✕ Inappropriate types: Using integer instead of bigint for IDs, or timestamp without timezone.
MEDIUM — Concurrency & Pooling

Connection exhaustion and deadlocking risks.

  • ✕ Long-running transactions: Keeping database transactions open across external HTTP API calls.
  • ✕ Connection pool leaks: Not releasing clients back to the connection pool on exception paths.
  • ✕ Unindexed RLS policy columns: Writing RLS filter rules on columns lacking dedicated indexes.
LOW — Naming & Migration Reversibility

Operational conventions and documentation.

  • ✕ Non-snake-case identifiers: Quoted mixed-case table or column names like "createdAt".
  • ✕ Missing down migrations: Schema changes that cannot be safely rolled back if deployment aborts.
04 — Decision process

How database-reviewer evaluates migration pull requests

  1. Step 1
    DDL Inspection

    Analyzes every CREATE, ALTER, and DROP command in the migration delta.

    Detect schema changes
  2. Step 2
    Foreign Key Audit

    Confirms every newly introduced foreign key column has a supporting index.

    FK indexing rule
  3. Step 3: RLS
    Security & Multi-Tenancy

    Ensures multi-tenant tables enforce Row Level Security with optimized auth.uid() checks.

    Zero cross-tenant leaks
  4. Step 4
    Query Profiling

    Checks application queries (ORM or SQL) for N+1 loops and missing filters.

    N+1 prevention
  5. Step 5
    Verdict

    APPROVE on safe DDL and indexed FKs; BLOCK on unindexed foreign keys or missing RLS.

    Production protection
05 — When it runs

Real-world scenarios where database-reviewer engages

1. Adding a new relational table

When adding an orders table referencing users(id), it ensures an index exists on orders.user_id and validates cascade delete rules.

2. Adding a NOT NULL column in prod

Warns against running ALTER TABLE users ADD COLUMN status text NOT NULL; without a default value, which would lock the table and fail if existing rows exist.

3. Supabase Row Level Security policy

Audits RLS policies like USING (auth.uid() = user_id) to ensure (SELECT auth.uid()) subquery optimization is used to prevent per-row evaluation overhead.

06 — Output format

Structured database finding & SQL remediation

[CRITICAL] Missing index on foreign key column
File: supabase/migrations/20260920000000_add_comments.sql:12
Issue: Table `comments` references `posts(id)` via foreign key `post_id`, but has no index on `post_id`. Any delete on `posts` will trigger a sequential scan of `comments`.
Fix: Create an index on `comments(post_id)`.
-- BAD: Foreign key declared without matching index
CREATE TABLE comments (
  id bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  post_id bigint REFERENCES posts(id) ON DELETE CASCADE
);

-- GOOD: Supporting index prevents sequential table scan
CREATE INDEX idx_comments_post_id ON comments(post_id);

07 — Strict boundaries

What database-reviewer does NOT do

No live database mutations

The reviewer never runs destructive DDL on your production database. It inspects local SQL and code changes statically.

UI & API handlers

Component styling and HTTP routing logic are outside scope; those are inspected by react-reviewer and typescript-reviewer.

Secret provisioning

Managing database credentials, environment variables, and vault secrets belongs to security-reviewer.
