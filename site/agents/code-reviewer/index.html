01 — What it is

A read-only inspector powered by Claude 3.5 Sonnet

The code-reviewer is an AI persona — a specialized prompt persona tuned for objective engineering critique. It runs in an isolated, read-only mode so it can never accidentally overwrite, commit, or break your working branch.

Read
File inspection

Reads full files around changes to understand imports, caller functions, and surrounding architectural context.

Grep
Pattern search

Searches across the entire repository for function usage, variable names, and potential breaking call sites.

Glob
File discovery

Discovers related project files matching patterns like configuration files, type declarations, or test suites.

Bash
Git inspection

Executes non-destructive inspection commands like git diff and git log to see what changed.

Glossary for non-coders: Diff: the list of exact line additions and deletions in your pull request. · Pull Request (PR): proposed code changes ready to merge into main. · Persona: a dedicated system instruction set that gives the model specialized reviewer instincts.

03 — Review checklist

What the reviewer looks for in your diff

Sourced directly from agents/code-reviewer.md, issues are organized by severity from catastrophic threats down to polish.

CRITICAL — Security & Vulnerabilities

Flaws that can cause data leakage, theft, or server takeovers. Must be fixed.

  • ✕ Hardcoded secrets: API keys, database tokens, or private passwords committed in source files.
  • ✕ Injection attacks: Raw string concatenation in database queries instead of parameterized statements.
  • ✕ Unsanitized output (XSS): Rendering untrusted user content directly in HTML without sanitization.
  • ✕ Auth bypasses: Publicly exposed backend endpoints missing permission or authentication gates.
HIGH — Quality & Architecture

Structural flaws that create production bugs, memory leaks, or maintainer friction.

  • ✕ Deep nesting & giant functions: Logic nested more than 4 levels deep or single functions over 50 lines.
  • ✕ Missing error boundaries: Swallowed exceptions, empty catch blocks, or unhandled Promise rejections.
  • ✕ React lifecycle bugs: Missing dependency arrays in hooks, state updates during render, and stale closures.
  • ✕ Debug remnants: Stray console.log statements or commented-out dead code.
MEDIUM — Performance & Edge Cases

Efficiency bottlenecks and incomplete user experience handling.

  • ✕ Missing state handling: Asynchronous data fetches without visual loading skeletons or error messages.
  • ✕ Array key reordering: Using array index as a React component key when list items can be sorted or deleted.
  • ✕ Accidental re-renders: Heavy mathematical computations executed on every render cycle without memoization.
LOW — Polish & Hygiene

Project hygiene conventions that keep codebases approachable.

  • ✕ Untracked TODOs: TODO or FIXME comments that do not reference a tracking issue ticket number.
  • ✕ Cryptic naming: Single-letter variables (x, tmp, data) used in non-trivial business logic contexts.
  • ✕ Missing public docs: Exported library functions lacking documentation explaining parameters.
04 — Decision process

The 5-step evaluation & confidence filter

LLM reviewers often drown PRs in speculative nits. The code-reviewer applies an explicit pre-report gate: only issues with >80% confidence and concrete proof are ever output.

  1. Step 1
    Diff Scope

    Inspects only changed files via git diff, plus callers and imports.

    No full-repo scans
  2. Step 2
    Checklist Scan

    Evaluates code against security, quality, React, and project conventions.

    Critical → Low
  3. Step 3: Gate
    >80% Confidence

    Must cite exact line number, specific failure scenario, and why existing types do not catch it.

    Drops speculative nits
  4. Step 4
    Severity Table

    Aggregates counts into Critical, High, Medium, and Low buckets.

    Structured summary
  5. Step 5
    Final Verdict

    Emits clear verdict: APPROVE, WARNING, or BLOCK.

    Clean review = APPROVE
05 — When it runs

Concrete scenarios where this agent is invoked

1. Adding a new API feature

When an issue adds a new data endpoint and client form, the reviewer checks for input sanitization, error responses, and clean component state separation.

2. Refactoring legacy code

When simplifying an overloaded utility, the reviewer ensures caller compatibility, checks that dead code was cleanly pruned, and verifies no unintended behavioral regressions occurred.

3. Edge-case bug patches

When patching a subtle bug, the reviewer confirms the fix directly addresses the root cause without introducing unhandled null states or bypassing existing security checks.

07 — Strict boundaries

What code-reviewer does NOT do

Never rewrites code

The reviewer is strictly an analytical observer. It never edits files, reformats whitespace, or commits fixes. Corrections are made by developers or earlier build stations.

Skipped, never simulated

If an agent persona is missing from disk, the pipeline records it as skipped — it never fakes an expert's review. Truthfulness over synthetic approval.

Narrow lane boundaries

Deep threat modeling belongs to security-reviewer, framework-specific build crashes belong to build resolvers, and test-first drafting belongs to tdd-guide.
