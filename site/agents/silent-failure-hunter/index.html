01 — What it is

The dedicated predator of hidden bugs and swallowed errors

When code silently catches an error and returns an empty list (.catch(() => [])) or logs a vague string without the cause, bugs become invisible until data is corrupted. The silent-failure-hunter hunts down these deceptive patterns.

Read
Control Flow Analysis

Reads the entire catch block, tracing whether errors are properly logged, wrapped with cause, or propagated.

Grep
Empty Catch Scanner

Discovers regex signatures of empty catches: catch {}, catch (e) {}, and silent fallback returns.

Glob
I/O Surface Discovery

Identifies all network calls, database queries, file system accesses, and external integration points.

Bash
Linter Inspection

Runs project linters checking for no-empty rules and unhandled promise rejections.

Glossary for non-coders: Swallowed Error: when software experiences a failure but wraps it in code that pretends nothing went wrong, hiding real crashes. · Lost Stack Trace: re-throwing a new error without passing the original error, making it impossible to see where the code failed. · Dangerous Fallback: returning an empty array or fake default when a service is completely down.

03 — Hunt Targets & Checklist

The 5 core hunt targets

Sourced directly from agents/silent-failure-hunter.md, focused on eliminating deceptive error suppression.

CRITICAL — Empty Catch Blocks

Completely swallowing errors and leaving no diagnostic trail whatsoever.

  • ✕ Empty catch blocks: catch {} or catch (err) {} with zero handling or logging.
  • ✕ Converting errors to null: Returning null without logging or letting callers distinguish empty vs failure.
  • ✕ Empty arrays on fetch fail: Returning [] when backend services fail, masking complete outages.
HIGH — Error Propagation & Stack Loss

Destroying diagnostic context and obscuring the original site of failure.

  • ✕ Lost stack traces: Throwing new Error("query failed") without passing { cause: originalError }.
  • ✕ Generic rethrows: Catching a specialized database error and converting it to generic 500 error.
  • ✕ Missing async rejection handling: Failure to handle Promise errors in background cron jobs or loops.
MEDIUM — Dangerous Fallbacks & Rollbacks

Graceful-looking fallback values that make downstream bugs harder to diagnose.

  • ✕ Blind fallbacks: Using .catch(() => false) where consumers treat false as a valid domain status.
  • ✕ Missing transaction rollback: Failing to abort or rollback database transactions on exception paths.
  • ✕ Missing I/O timeouts: Network or database fetch calls without abort signals or connection timeouts.
LOW — Inadequate Logging Metadata

Log quality and telemetry hygiene.

  • ✕ Log-and-forget: Logging an error and then continuing execution as if nothing happened.
  • ✕ Wrong log severity: Logging critical database connection drops with console.log or info level.

05 — When it runs

Real-world scenarios where silent-failure-hunter saves production

1. Third-party payment webhooks

A webhook handler catches an error when crediting user balance, logs "error handled", and returns HTTP 200. The user never gets credited, but Stripe thinks the webhook succeeded. The hunter blocks this immediately.

2. Cache fallbacks hiding DB outages

Code catches database errors and returns empty cache data. Sentry never receives an alert while the database is on fire because the errors are swallowed in silence.

3. Lost file upload failures

S3 upload fails with 403 Forbidden, but catch block transforms the response into { avatarUrl: null } without an exception, causing user profiles to save blank photos.

06 — Output format

Standard 5-point finding format

[CRITICAL] Swallowed database error with dangerous empty fallback
Location: src/services/billing.ts:42
Severity: CRITICAL
Issue: Catch block catches error during invoice calculation and returns [] without logging or re-throwing.
Impact: Invoices will be calculated as $0.00 during transient DB hiccups with zero alerts in logging pipelines.
Fix recommendation: Re-throw custom BillingError with original error attached via { cause: error }.
// BAD: Swallows failure and returns misleading empty list
try {
  return await db.invoices.findMany();
} catch (err) {
  return []; // Silent failure
}

// GOOD: Propagates error with context and preserved stack trace
try {
  return await db.invoices.findMany();
} catch (err) {
  throw new InvoiceFetchError('Failed to fetch invoices', { cause: err });
}

07 — Strict boundaries

What silent-failure-hunter does NOT do

Does not rewrite code

The hunter reports violations and provides exact code recommendations, but never edits project files directly.

Ignores valid fallbacks

Intentional, documented offline caches or circuit breakers with full telemetry are recognized as valid architecture.

Does not manage APM servers

It audits application code error paths, not external monitoring SaaS infrastructure (Datadog/Sentry) setup.
